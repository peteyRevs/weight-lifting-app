# Simulator builds for arm64 only (2026-10-18)

Branch `ci/arm64-only`, cut from `origin/main` at `5070b5b`. It replaces the shelved main warm-up job
(branch `worktree-agent-a92dc1ccb90626738` at `646c66f`, record `tasks/chores/2026-10-17-main-cache.md`
there). That job cost about as many billed minutes per merge as it saved on each PR's first run, and the
coordinator ruled it out on 2026-10-18 because the product owner asked for the cheapest option. Its profiling
found this lever, which has no recurring cost.

## The problem

`check.sh`'s iOS `build-for-testing` (scheme `Ledger`) also builds the embedded watch app. Debug builds set
`ONLY_ACTIVE_ARCH=YES`, but the active arch comes from the run destination, an iPhone simulator. The watch
targets build for the watch simulator SDK, where no destination says which arch is active, so they build
`ARCHS_STANDARD`: arm64 and x86_64. In the build log that shows as 16 `SwiftDriver … normal x86_64` modules
(the watch app's package modules) and `CreateUniversalBinary` steps. Nothing ever runs the x86_64 slice: every
simulator here, on a developer Mac and on the `xcode-27` image, is Apple silicon.

### Why `EXCLUDED_ARCHS[sdk=watchsimulator*]=x86_64` did nothing

xcodebuild splits a command-line setting at its first `=`. The condition `[sdk=…]` contains one, so the
argument parsed as a setting named `EXCLUDED_ARCHS[sdk` whose value is `watchsimulator*]=x86_64`.
`-showBuildSettings` with that argument prints `EXCLUDED_ARCHS = watchsimulator*]=x86_64`: it excludes an arch
of that name, which matches nothing. A conditional setting works only from an xcconfig or the project, and
this chore may change neither.

## The change

- `scripts/check.sh`: `test_platform`'s shared arguments now end with `ARCHS=arm64`. It is the narrowest
  mechanism that actually takes effect: a command-line setting outranks every target's own, the watch
  targets included, and sits in the one argument list both `build-for-testing` and `test-without-building`
  use. So the test run is always given the build it ran after, on both lanes, locally and in CI. The watch
  lane built only arm64 already (its destination is a watch simulator); the argument changes nothing there.
  `ONLY_ACTIVE_ARCH` is already `YES` and is what stops at the platform boundary, so it is no lever.
- Tester file `scripts/tests/adversarial/check-wiring.adv.sh`:
  - W76 is new. Every `build-for-testing` and `test-without-building` on both lanes, in the full gate and
    under `--ios-only`, passes `ARCHS=arm64` exactly once. Each test run's arguments equal its build's,
    leaving out the action, the result bundle and what follows it.
  - Brought over from the shelved branch: the suite now unsets `LEDGER_COMPILATION_CACHE` at its start. W65's
    "unset" case otherwise inherits a caller's export: the first full gate on the shelved branch, run with the
    variable exported, failed there.
- `docs/ci-cd.md`: an "arm64 only" bullet under CI efficiency.
- Not changed: the pbxproj, the xcconfigs, the test plans, `pr.yml`, `nightly.yml`.

## Measured

Developer Mac, under the simulator lock. Each run is `check.sh`'s iOS `build-for-testing` with its own
arguments plus `COMPILATION_CACHE_ENABLE_CACHING=YES` and `-showBuildTimingSummary` (scratchpad `arch.sh`).
Before every build, everything under `.derivedData` was deleted except `SourcePackages`, and except the cache
for a warm build. Every tracked file under `Apps` and `LedgerKit` was then touched, as a fresh checkout would
leave it. Two rounds of each. The machine was shared (load average 13–24), so wall times are noisy; task
counts are not.

| | Before | After (`ARCHS=arm64`) |
|---|--:|--:|
| Swift compile tasks | 546 | 422 |
| Swift modules (driver tasks) | 75 | 59 |
| Links | 81 | 63 |
| x86_64 modules | 16 | 0 |
| Compile task time, cold | 824–945 s | 706–805 s |
| Wall, cold | 116–142 s | 107–114 s |
| Wall, warm | 29–57 s | 23–28 s |
| Driver task time, warm | 67–102 s | 49–67 s |
| Link task time, warm | 30–100 s | 26–41 s |
| Cache after a cold build | 1,510 MB | 1,246 MB |

The cold compile work fell by about 14% and the warm build's driver and link work by about a fifth. On the
3-core runner, where task time rather than wall time sets the build, the expected saving is in the same range:
about 130–200 s of a 937–1,458 s cold first run, and about 80–150 s of a 452–760 s warm one. That is an
estimate; the runner's figure arrives with the first PR run after this merges. The compressed cache should
shrink about as much (1.5 GB was 452 MB through `tar | zstd`), so restoring and saving it take slightly less.

Each cache entry's key hashes the compiler's arguments, so every entry made before this change misses after
it. Because no cache is saved on `main`, a PR's caches come only from its own runs, and a PR opened after the
merge starts fresh either way. A PR already open when this merges builds cold once more, on its first push
after rebasing.

## The nightly

`nightly.yml` calls `xcodebuild` itself, without `check.sh`, so it still builds the watch modules for both archs.
That costs it the same extra minutes per run, and nothing else: it is run by hand, its timeouts are not tight,
and its tests run the arm64 slice like every lane. Bringing it in line is a one-argument change for a later
nightly edit, which this chore was told not to make.
