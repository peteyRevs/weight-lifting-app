## 1. Project generation

### XcodeGen
- Latest release **2.46.0, 2026-07-16** (GitHub API; https://github.com/yonaskolb/XcodeGen/releases). MIT. Actively maintained: commits on 2026-09-13, unreleased "Next Version" section in CHANGELOG with fixes for `syncedFolder` source paths (#1636) and non-deterministic nested-attribute serialization (#1639) (https://github.com/yonaskolb/XcodeGen/blob/master/CHANGELOG.md).
- Xcode 16 synchronized ("buildable") folders: supported since 2.44.0 via `type: syncedFolder` on a target source; requires `projectFormat: xcode16_0` or later; `explicitFolders` + `excludes` supported (2.45.0); documented `projectFormat` values go up to `xcode16_3` (https://github.com/yonaskolb/XcodeGen/blob/master/Docs/ProjectSpec.md).
- SPM: local packages via `packages: {Name}: path: ...`; targets depend with `package: Name` (+ `product`/`products`); Swift package **traits** supported since 2.46.0.
- watchOS: `watchOS` is a supported platform; product types include `application` (modern single-target watch app), `application.watchapp2`, `application.watchapp2-container`, `watchkit2-extension`. Multi-destination app targets do **not** support the watchOS destination — you create a separate `platform: watchOS` target (ProjectSpec.md).
- **Blocking bug for iPhone+Watch apps on Xcode 26:** issue #1613 (open since 2026-04-02) — the generated "Embed Watch Content" copy phase uses `dstSubfolderSpec = 16` + `dstPath = "$(CONTENTS_FOLDER_PATH)/Watch"`; Xcode 26 fails install with "…is a Foundation extension and must be embedded in the parent app bundle's PlugIns directory". Fix PR #1614 is still **open/unmerged** (https://github.com/yonaskolb/XcodeGen/issues/1613 , https://github.com/yonaskolb/XcodeGen/pull/1614). Workarounds: (a) ProjectSpec documents a per-dependency `copy: {destination: plugins}` override that "only applies when `embed` is true", and the generator source checks `dependency.copyPhase` before the watchOS special case (`Sources/XcodeGenKit/PBXProjGenerator.swift` around lines 767–787) — **UNCONFIRMED** that this yields a working install; test it first; (b) a post-generate patch of `project.pbxproj` (the issue thread mentions this); (c) build XcodeGen from the PR branch.
- Xcode 27 support: no issues/PRs mention Xcode 27 yet — **UNCONFIRMED**.
- Xcode Cloud: an XcodeGen repo without a committed `.xcodeproj` needs `ci_scripts/ci_post_clone.sh` that installs XcodeGen and runs `xcodegen generate` (Apple: https://developer.apple.com/documentation/xcode/writing-custom-build-scripts ; examples: https://www.polpiella.dev/xcode-cloud-scripts-fastlane-and-cocoapods/).
- Install/pin: `brew install xcodegen` or `mise use xcodegen@2.46.0` (aqua backend, https://mise-versions.jdx.dev/tools/xcodegen).

Repo LICENSE.md: MIT for everything **except** `server/`, `kura/`, `atlas/` which are **MPL-2.0** (https://github.com/tuist/tuist/blob/main/LICENSE.md). No Tuist issue found; whether it fails is **UNCONFIRMED** — verify on Xcode 26.6 before choosing Tuist.

### Xcode 16+ synchronized folders (no generator)
- `PBXFileSystemSynchronizedRootGroup` records only the folder path; adding/removing files no longer edits `project.pbxproj`; exceptions via `PBXFileSystemSynchronizedBuildFileExceptionSet` (https://pepicrft.me/blog/2024/07/20/how-synchronized-groups-work-at-the-pbxproj-level ; https://tuist.dev/blog/2025/03/21/git-conflicts). Xcode 26 fixed non-deterministic file ordering in synchronized groups that caused rebuilds (Xcode 26 release notes, 123839235).
- Tooling compatibility: fastlane's "unknown ISA PBXFileSystemSynchronizedRootGroup" issue #22265 closed 2026-05-10; Xcodeproj gem 1.28.0 (2026-07-06) added the objectVersion for Xcode 26.3 (https://github.com/CocoaPods/Xcodeproj/releases).

### Recommendation (Q1)
With thin app targets and all logic in local Swift packages, the `.pbxproj` is small and changes rarely (only when targets/settings change). Use **XcodeGen** (`project.yml` is the single text source of truth, MIT, no server, trivial for agents to edit) with `type: syncedFolder` sources for the iOS and watchOS app targets and `packages:` for local SPM packages; `.gitignore` the generated `.xcodeproj`; pin XcodeGen via mise; add a CI step that regenerates and fails on unexpected diffs, and `ci_scripts/ci_post_clone.sh` for Xcode Cloud. Agents adding files never touch the project at all (synced folders), and adding a package target only touches `Package.swift`. **Gate:** before committing to XcodeGen, prove the watchOS embed workaround (#1613) on Xcode 26.6 — if it can't be made to work, fall back to a hand-created committed `.xcodeproj` using buildable folders (zero generator risk; only target/setting changes touch the pbxproj). Tuist is the right choice only if you want its paid cache/selective-testing later; its manifests are heavier and it has the same watch-embed code path to verify.

## 2. Testing

### Swift Testing — what shipped
- **Xcode 26 (Swift 6.2)** release notes (https://developer.apple.com/documentation/xcode-release-notes/xcode-26-release-notes): exit tests ("test code that calls `fatalError()`/`exit()`" — `#expect(processExitsWith:)`); attachments ("attaching files or data… shown in Xcode's Test Report and included in .xcresult"); `swift test --attachments-path`; runtime-issue detection surfaced in Xcode/xcodebuild; `ConditionTrait.evaluate()`; new trait for customizing issue handling; parameterized test progress/counts in console. Community: exit tests run on macOS/Linux, not iOS (https://dev.to/arshtechpro/xcode-26-exit-tests-testing-fatal-errors-and-crashes-safely-263k); test-scoping traits arrived in Swift 6.1 (https://www.pointfree.co/blog/posts/169-new-in-swift-6-1-test-scoping-traits).
- **Swift 6.3 (2026-03-24)**: `Issue.record(_, severity: .warning)`, `Test.cancel()`, image attachments via cross-import overlays (https://www.swift.org/blog/swift-6.3-released/).
- **Swift 6.4 / Xcode 27 (2026-09-14/15)**: XCTest ⇄ Swift Testing interoperability (ST-0021: `XCTAssert` inside `@Test`, `#expect` inside `XCTestCase`; test-plan "Swift Testing and XCTest Interoperability" setting), `CustomTestReflectable`, test repetition from `swift test`, `Transferable` attachments; Xcode 27 also adds `XCUIVoiceOverService` for UI tests and big perf gains for large parameterized suites (https://www.swift.org/blog/swift-6.4-released/ ; Xcode 27 release notes; https://developer.apple.com/videos/play/wwdc2026/267/).

### Running Swift Testing tests
- `swift test` in each package: verified flags on the local 6.3.3 toolchain — `--enable-swift-testing/--disable-swift-testing`, `--enable-xctest/--disable-xctest`, `--parallel`, `--num-workers N`, `--filter <regex>`, `--enable-code-coverage`, `--attachments-path <dir>`. Swift Testing suites already run in parallel by default (https://developer.apple.com/documentation/testing/migratingfromxctest).
- `xcodebuild test -scheme <PackageOrApp> -destination '…'` runs XCTest + Swift Testing in packages and app test bundles (Xcode 16+). `-only-testing:` identifiers for Swift Testing carry trailing parentheses, e.g. `Target/Suite/testName()` (https://trinhngocthuyen.com/posts/tech/swift-testing-and-xcodebuild/).
- Verified `xcodebuild` options on 26.6: `-parallel-testing-enabled YES`, `-parallel-testing-worker-count`, `-enableCodeCoverage YES`, `-only-testing`/`-skip-testing`, `-retry-tests-on-failure`, `-test-iterations N`, `-test-timeouts-enabled`; the `build-for-testing` and `test-without-building` actions remain (man page: https://leancrew.com/all-this/man/man1/xcodebuild.html ; xctestrun format: https://keith.github.io/xcode-man-pages/xcodebuild.xctestrun.5.html). Pattern: `build-for-testing` once, then `test-without-building -xctestrun … -destination …` per simulator.
- Result bundles (Xcode 16+): `xcrun xcresulttool get test-results summary|tests|test-details|activities|insights|metrics --path Result.xcresult` (verified locally); old `get object --format json` needs `--legacy` (https://developer.apple.com/forums/thread/763888). Coverage: `xcrun xccov view --report --json Result.xcresult` (verified locally). Pretty logs: xcbeautify 3.2.1 (2026-04-04; preinstalled on GitHub macOS images).
- Coverage thresholds: no native xcodebuild flag. Options: a jq script over `xccov view --report --json` (fail if `lineCoverage` < N); fastlane-community/xcov `--minimum_coverage_percentage` (raises if under; xcresult-from-Xcode-26 support **UNCONFIRMED**, https://github.com/fastlane-community/xcov); elegantchaos/Coverage `--threshold` (https://github.com/elegantchaos/Coverage); Codecov/Sonar uploads. Xcode Cloud's test report has a Coverage section (June 6, 2025 release note).

### Snapshot testing
- pointfreeco/swift-snapshot-testing **1.19.5, 2026-09-15** (fix "watchOS compile error: 'Image' not in scope"); 1.19.0 (2026-03-18) added Swift Testing attachment support and `record: .missing/.all/.failed` (deprecates `isRecording`); 1.19.1 uses native Swift Testing image attachments on Swift ≥ 6.3 (https://github.com/pointfreeco/swift-snapshot-testing/releases). Swift Testing usage: `@Test func x() { assertSnapshot(of: view, as: .image) }` with `withSnapshotTesting(record:)` / `.snapshots(record:)` trait (https://www.pointfree.co/blog/posts/146-swift-testing-support-for-snapshottesting). Snapshot tests must run on a fixed simulator (device + OS pinned) to be deterministic.

### Accessibility audits (XCUITest)
- `XCUIApplication.performAccessibilityAudit(for: XCUIAccessibilityAuditType = .all, _ issueHandler:)` — Apple docs list iOS 17+, macOS 14+, tvOS 17+, visionOS, **watchOS 10+**, Xcode 16.3+ (https://developer.apple.com/documentation/xcuiautomation/xcuiapplication/performaccessibilityaudit(for:_:)). Audit types: contrast, elementDetection, hitRegion, sufficientElementDescription, dynamicType, textClipped, trait (https://developer.apple.com/videos/play/wwdc2023/10035/). Use the issue handler to whitelist known false positives.

### watchOS tests in CI
- Apple: add a "watchOS Unit Testing Bundle" / "watchOS UI Testing Bundle" target to the watch app; tests run in the watch simulator via the generated scheme (https://developer.apple.com/documentation/watchos-apps/setting-up-tests-for-your-watchos-app).
- `xcodebuild test -scheme LedgerWatch -destination 'platform=watchOS Simulator,name=Apple Watch Series 11 (46mm),OS=26.5'`. GitHub's macos-26 image preinstalls watchOS 26.2/26.4/26.5 runtimes (see §4), so no download step is needed there. Locally you have only watchOS 26.5; install iOS with `xcodebuild -downloadPlatform iOS` (`-buildVersion` takes a build number such as `23F77`; `26.5` is rejected as "not available" — verified 2026-09-19) (https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components); runtimes are ~5–8 GB each (https://developer.apple.com/forums/thread/765478).
- Put pure logic in platform-agnostic packages so most tests run via `swift test` on macOS (fast, no simulator); keep simulator-bound tests (SwiftUI snapshots, HealthKit-facing code, UI tests) small.

## 3. Lint / format

- **SwiftLint 0.65.1, 2026-08-21** (0.65.0 2026-06-27; 0.64.0 added Windows) (https://github.com/realm/SwiftLint/releases). MIT. Its `Package.swift` pins `swift-syntax` **605.0.0-prerelease-2026-06-26**, i.e. it parses Swift 6.3/6.4-era syntax; 0.65.0 needs Swift ≥ 6.1 to build the test suite. Install: `brew install swiftlint` or prebuilt binary; SPM plugin `SwiftLintBuildToolPlugin` (SwiftLintPlugins) for in-Xcode warnings; `swiftlint --strict` turns warnings into errors (README). Config keys: `opt_in_rules`, `only_rules`, `analyzer_rules` (run via `swiftlint analyze --compiler-log-path`). Recommended strict baseline (my recommendation, not a sourced config): `--strict` in CI; `opt_in_rules` including `explicit_init`, `first_where`, `force_unwrapping`, `implicitly_unwrapped_optional`, `unowned_variable_capture`, `closure_body_length`, `empty_count`, `sorted_imports`, `unhandled_throwing_task`, `private_outlet`, `redundant_final`, `variable_shadowing` (new in 0.63.3); `analyzer_rules: [unused_declaration, unused_import]`; `excluded: [.build, DerivedData, **/Generated]`.
- **SwiftFormat (nicklockwood) 0.63.0, 2026-08-30** (https://github.com/nicklockwood/SwiftFormat/releases). MIT. `swiftformat --lint . --reporter github-actions-log` for CI (README); set `--swift-version 6.3` and `--language-mode 6` (or a `.swift-version` file) so rules behave for Swift 6 language mode. CHANGELOG already references Swift 6.4 behaviour. Preinstalled on GitHub macOS images (0.63.0).
- **apple/swift-format**: bundled in the Xcode toolchain since Xcode 16 (Sept 2024) (https://kingskode.medium.com/xcode-16-now-comes-with-swift-format-out-of-the-box-5fb5e5c8c839); verified on Xcode 26.6: `xcrun swift-format --version` → 6.3.0; `swift-format lint --strict --recursive --parallel` exists (`-s/--strict` "Treat all findings as errors"). Standalone releases: 604.0.0 (2026-09-16), 603.0.0 (2026-06-30) — major version must match the toolchain's swift-syntax (https://github.com/swiftlang/swift-format). Verdict: pick **one** formatter. `swift-format` has the zero-install advantage (ships with Xcode) and a sanctioned style; SwiftFormat has far more rules and better SwiftUI-specific cleanup. For an agent-heavy repo the deciding factor is determinism across machines — the toolchain-bundled `swift-format` version drifts with Xcode, whereas SwiftFormat/SwiftLint are pinned via mise. Recommend **SwiftFormat (pinned) + SwiftLint (pinned, `--strict`)**.
- Pre-commit approach (2026): pin tools with **mise v2026.9.10** (`mise.toml`: swiftlint, swiftformat, xcodegen, lefthook, xcbeautify; `mise install`) (https://mise.jdx.dev/lang/swift.html , https://tuist.dev/blog/2025/02/04/mise); run hooks with **lefthook v2.1.14, 2026-09-14** (Go, parallel, `lefthook.yml` committed, `lefthook install`) (https://github.com/evilmartians/lefthook/releases). Both SwiftLint and SwiftFormat also ship `.pre-commit-hooks.yaml` for the Python `pre-commit` framework (https://github.com/realm/SwiftLint/blob/main/.pre-commit-hooks.yaml , https://github.com/nicklockwood/SwiftFormat/blob/main/.pre-commit-hooks.yaml). Hooks run on staged files only; CI re-runs `swiftformat --lint` and `swiftlint --strict` on the whole tree as the real gate (hooks are a convenience, not a control).

### Xcode Cloud (2026)

### Recommendation (Q4)
Split by strength: **GitHub Actions for PR gates** (`macos-26`, `DEVELOPER_DIR` pinned to Xcode 26.6; jobs: format/lint → `swift test --parallel --enable-code-coverage` per package → `xcodebuild build-for-testing` once, then `test-without-building` on one iOS 26.5 and one watchOS 26.5 simulator with `-resultBundlePath`, `xcresulttool` summary + coverage threshold script; required status checks for merge), and **Xcode Cloud for delivery** (workflow A: branch=main → archive + TestFlight internal; workflow B: tag `v*` → archive + TestFlight external/App Store submission) because it needs no signing secrets and the 25 free hours cover a solo team's release builds. Keep the repo public if possible (macOS minutes free); otherwise budget ~$0.62 per 10-minute PR job or move PR testing to Xcode Cloud too if the 25 h suffice (25 h ≈ 1,500 min/month). Run pure-Swift package tests on `ubuntu-latest` ($0.006/min) only if those packages avoid Apple-only frameworks.

## 5. Release automation

- **fastlane 2.240.1, 2026-09-15** (2.240.0 2026-09-14; 2.239.0 2026-09-04 raised the minimum to **Ruby ≥ 3.1**; 2.238.0 added Ruby 4 support) (https://github.com/fastlane/fastlane/releases). MIT, very active (commits on 2026-09-16). Docs: "supports Ruby versions 3.1 or newer, but prefers Ruby 3.3 or greater"; "system Ruby is not recommended"; "The preferred method is with Bundler" (https://docs.fastlane.tools/getting-started/ios/setup/). Your system Ruby 2.6 cannot run it: install Ruby 3.3+/3.4 via `mise use ruby@3.4` (or Homebrew `ruby`), commit `Gemfile` + `Gemfile.lock`, run `bundle exec fastlane`. GitHub's macOS image has Ruby 3.4.10 and fastlane 2.239.0 preinstalled but you should still `bundle install` for a pinned version. `brew install fastlane` works but is unpinned — avoid for CI.
- Auth: App Store Connect API key (Team key recommended; `.p8` downloadable once) via `app_store_connect_api_key(key_id:, issuer_id:, key_filepath:|key_content:)`; supported by `pilot`, `deliver`, `match`, `sigh`, `cert`, `download_dsyms`, `app_store_build_number`; `precheck` (except IAP) still needs an Apple ID (https://docs.fastlane.tools/app-store-connect-api/).
- Signing options: (1) **Xcode Cloud managed/cloud signing** — nothing to store; (2) **fastlane match** — certs/profiles encrypted in git/S3/GCS/GitLab secure files/Azure, `readonly: true` in CI, works with API keys; note Xcode 16 moved profiles to `~/Library/Developer/Xcode/UserData/Provisioning Profiles` and `match nuke` breaks Ad Hoc/Enterprise builds (https://docs.fastlane.tools/actions/match/); (3) **Xcode-native**: `xcodebuild -exportArchive -exportOptionsPlist` with `method: app-store-connect`, `signingStyle: automatic`, `destination: upload`, `uploadSymbols`, `manageAppVersionAndBuildNumber`, `testFlightInternalTestingOnly: true` (all verified in `xcodebuild -help` on 26.6) — this uploads without fastlane, using Xcode's cloud signing when run on a machine signed into the account (on CI you'd still need a key/cert in the keychain or Xcode Cloud).
- TestFlight/App Store via fastlane: `pilot` (upload + distribute to groups, changelog, `skip_waiting_for_build_processing`), `deliver` (metadata, screenshots, submission). `altool` is deprecated only for **notarization** (uploads rejected since 2023-11-01; use `notarytool`) but still ships in Xcode 26.6 (`altool --upload-package`) (https://developer.apple.com/documentation/technotes/tn3147-migrating-to-the-latest-notarization-tool).
- App Store Connect API build uploads: since API 4.1 (WWDC25) you can upload builds directly via `POST /v1/buildUploads` + `buildUploadFiles` from any language (https://developer.apple.com/documentation/appstoreconnectapi/build-uploads , https://developer.apple.com/videos/play/wwdc2025/324/); API 4.4.1 release notes dated 2026-07-15 (https://developer.apple.com/documentation/appstoreconnectapi/app-store-connect-api-4-4-1-release-notes).
- "App Store Connect CLI": **no official Apple CLI found** (App Store Connect updates on 2026-06-18/06-25/09-14 announce no CLI; **UNCONFIRMED negative**). The popular `asc` is **unofficial**: rorkai/App-Store-Connect-CLI by Rudrank Riyam, MIT, Go, `brew install asc`, v5.3.4 on 2026-09-15, 76 command groups over the ASC API incl. build upload, TestFlight, submissions, signing (https://github.com/rorkai/App-Store-Connect-CLI , https://asccli.sh/). Others: ittybittyapps/appstoreconnect-cli, codemagic-ci-cd/cli-tools, tddworks/asc-cli.
- Conventional-commit release notes: **release-please v17.11.2 (2026-08-24)** — GitHub Action that maintains a release PR, bumps version, writes CHANGELOG, creates the tag/GitHub Release (`release-type: simple` for non-package repos) (https://github.com/googleapis/release-please); **git-cliff v2.14.1 (2026-09-01)** — Rust changelog generator with templates, ideal for producing TestFlight "What to Test"/App Store release notes text in CI (https://github.com/orhun/git-cliff , https://0x5.uk/2026/03/12/automatic-release-notes-with-semantic-commits-and-git-cliff/); semantic-release v25.0.9 (v26 beta, Node) (https://github.com/semantic-release/semantic-release); fastlane-plugin-semantic_release (`analyze_commits`, `conventional_changelog`; last push 2026-03-18) (https://github.com/xotahal/fastlane-plugin-semantic_release).

### Recommendation (Q5)
Enforce Conventional Commits (commitlint or a lefthook `commit-msg` regex). Use **release-please** to open/merge release PRs on `main` and cut `vX.Y.Z` tags + GitHub Releases; the tag triggers the App Store workflow (Xcode Cloud tag-start condition, or GHA + fastlane `deliver` with the API key). Use **git-cliff** to render the TestFlight changelog from the same commits. Keep fastlane (Bundler-pinned) only for what Xcode Cloud can't do well: metadata/screenshots (`deliver`), dSYM download, and optional `match` if you ever move release builds to GitHub Actions.

## 6. Privacy manifest, HealthKit review, TestFlight rules

- **Privacy manifest** (`PrivacyInfo.xcprivacy`): since **2024-05-01** App Store Connect rejects uploads that use "required reason" APIs without declaring reasons; every executable/dynamic library that uses such an API needs its own manifest; a third-party SDK may not rely on the app's manifest (https://developer.apple.com/documentation/bundleresources/describing-use-of-required-reason-api). Keys: `NSPrivacyTracking`, `NSPrivacyTrackingDomains`, `NSPrivacyCollectedDataTypes`, `NSPrivacyAccessedAPITypes` (https://developer.apple.com/documentation/bundleresources/adding-a-privacy-manifest-to-your-app-or-third-party-sdk). Required-reason categories are file timestamps, system boot time, disk space, active keyboards and **UserDefaults** (HealthKit is *not* a required-reason API) — a workout app that touches `UserDefaults` must declare `NSPrivacyAccessedAPICategoryUserDefaults` with reason `CA92.1` (category/reason list per the Apple page above; I could not machine-extract the headings, so **verify codes there**). Collected data types for Ledger: `NSPrivacyCollectedDataTypeHealth` and `NSPrivacyCollectedDataTypeFitness` with `NSPrivacyCollectedDataTypePurposes` (e.g. `…PurposeAppFunctionality`), `NSPrivacyCollectedDataTypeLinked`, `NSPrivacyCollectedDataTypeTracking` (https://developer.apple.com/documentation/bundleresources/describing-data-use-in-privacy-manifests). Local SPM packages compiled statically into the app are covered by the app's manifest; a dynamic framework target needs its own.
- **Third-party SDKs**: Apple's list of ~86 "commonly used" SDKs (Alamofire, Firebase*, Lottie, Kingfisher, RxSwift, SnapKit, SDWebImage, RealmSwift, …) must ship a privacy manifest and, when used as binaries, a signature; new apps or updates adding them are rejected otherwise (https://developer.apple.com/support/third-party-SDK-requirements/). swift-snapshot-testing (test-only) and Apple frameworks are not on it. Xcode's Product ▸ Generate Privacy Report aggregates manifests for the nutrition label.
- **HealthKit App Review** (https://developer.apple.com/app-store/review/guidelines/): 5.1.3(i) no use/disclosure of HealthKit data for advertising, marketing, or use-based data mining; "You must disclose the specific health data that you are collecting from the device"; 5.1.3(ii) no false/inaccurate data written to HealthKit and **no personal health information stored in iCloud**; 5.1.3(iii)/(iv) consent + IRB for human-subject research; 5.1.2(vi) same no-marketing rule; 2.5.1 HealthKit must be used for health/fitness and integrate with the Health app. Info.plist: `NSHealthShareUsageDescription` (reading) and `NSHealthUpdateUsageDescription` (writing) — missing/vague strings are a common rejection; enable the HealthKit capability; Xcode adds `healthkit` to `UIRequiredDeviceCapabilities` (remove it if HealthKit is optional; the entry isn't used by watchOS apps) (https://developer.apple.com/documentation/healthkit/setting-up-healthkit ; https://developer.apple.com/documentation/BundleResources/Information-Property-List/NSHealthShareUsageDescription). Request only the HK types you actually use, each mapped to a visible feature (https://3nsofts.com/insights/healthkit-architecture-production-ios-apps). If Ledger syncs via CloudKit, do not put HealthKit-derived personal health data in iCloud (5.1.3(ii)).
- **TestFlight** (https://developer.apple.com/help/app-store-connect/test-a-beta-version/testflight-overview): up to **100 internal** testers (App Store Connect users) and **10,000 external** testers per app; builds expire after **90 days**. External testing: "The first build you submit requires a full review, but later builds for the same version might not"; only one build per version in review at a time; "You can submit up to six builds for TestFlight App Review within a 24-hour period"; Test Information (beta app description + feedback email) is required before external review (https://developer.apple.com/help/app-store-connect/test-a-beta-version/invite-external-testers , https://developer.apple.com/help/app-store-connect/test-a-beta-version/provide-test-information/). Internal groups need no review — use them for every `main` build; external groups only for tagged release candidates. Xcode Cloud external-TestFlight post-actions require a clean build (§4).

## Consolidated recommendation for Ledger

1. **Project**: XcodeGen 2.46.0 (pinned via mise) + `syncedFolder` sources for the thin `Ledger` (iOS) and `Ledger Watch App` (watchOS single-target) app targets; all features as local SPM packages under `Packages/`; `.xcodeproj` gitignored and regenerated (`make project`, CI drift check, `ci_scripts/ci_post_clone.sh`). **First spike:** verify the watch embed on Xcode 26.6 with `copy: {destination: plugins}`; if it fails, commit a hand-made project with buildable folders instead.
2. **Tests**: Swift Testing everywhere new; `swift test --parallel` per package; snapshot tests with swift-snapshot-testing 1.19.5 on pinned simulators; one XCUITest target per platform including `performAccessibilityAudit()` on key screens; `build-for-testing`/`test-without-building`; `xcresulttool get test-results summary` + `xccov` JSON threshold (start at e.g. 70% on owned packages, ratchet up).
3. **Lint/format**: SwiftFormat 0.63.0 (`--lint`, `--swift-version 6.3 --language-mode 6`) + SwiftLint 0.65.1 (`--strict`), pinned with mise, run by lefthook locally and as required CI checks.
4. **CI**: GitHub Actions `macos-26` for PR gates with `DEVELOPER_DIR` pinned to Xcode 26.6; Xcode Cloud for TestFlight (main) and App Store (tags). Watch for Xcode 27 support in XcodeGen/SwiftLint/SwiftFormat and the `xcode-27` runner label before moving.
5. **Release**: Conventional Commits → release-please tags → Xcode Cloud tag workflow (or fastlane `deliver`/`pilot` with an ASC API key, Bundler-pinned, Ruby 3.4 via mise); git-cliff for release notes.
6. **Privacy/review**: ship `PrivacyInfo.xcprivacy` in the app (Health/Fitness data types + UserDefaults reason), keep HealthKit data out of iCloud, precise usage strings, HealthKit capability on both targets; internal TestFlight for every main build, external only for RCs.
