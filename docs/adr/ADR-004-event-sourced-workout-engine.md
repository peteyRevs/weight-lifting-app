# ADR-004: Event-sourced live workout engine shared by phone and watch

**Status:** Accepted · **Date:** 2026-09-16

## Context

The prototype's headline is "phone + watch share one live workout". Both
devices can mutate the same in-progress workout at the same time: the watch
logs a set or nudges weight with the crown while the phone edits reps, adds a
set, swaps an exercise, or extends rest. Connectivity between the devices is
intermittent (phone in a locker, Bluetooth drop). The rest timer must read the
same on both screens and the watch must buzz at zero even with no phone.

Naively syncing "the current state" leads to lost updates and divergent
timers. We need a model where both devices converge to the same state without
a server.

## Decision

The live workout is an **append-only log of `WorkoutEvent`s** folded by a
**pure reducer** into `WorkoutState`. Both apps run the identical reducer from
`LedgerDomain`.

```swift
public enum WorkoutEvent: Codable, Sendable, Equatable {
    case started(workoutID: WorkoutID, templateID: SessionTemplateID?, at: Date)
    case exerciseSelected(slot: SlotID, at: Date)
    case setLogged(slot: SlotID, set: SetID, weight: Weight, reps: Reps, at: Date)
    case setUnlogged(slot: SlotID, set: SetID, at: Date)
    case setTargetChanged(slot: SlotID, set: SetID, weight: Weight?, reps: Reps?, at: Date)
    case setAdded(slot: SlotID, set: SetID, weight: Weight, reps: Reps, at: Date)
    case exerciseSwapped(slot: SlotID, to: ExerciseID, at: Date)
    case restStarted(endsAt: Date, at: Date)
    case restExtended(by: Duration, at: Date)
    case restSkipped(at: Date)
    case finished(at: Date)
    case discarded(at: Date)
}

public struct EventEnvelope: Codable, Sendable, Equatable, Comparable {
    public let event: WorkoutEvent
    public let device: DeviceID      // phone | watch
    public let seq: UInt64           // per-device monotonically increasing
    public let wallClock: Date       // for LWW ordering
}

public struct WorkoutEngine {
    public static func reduce(_ state: WorkoutState, _ envelope: EventEnvelope) -> (WorkoutState, [Effect])
}
```

Rules:

1. **Determinism.** `reduce` is pure. Effects (haptic, HealthKit write, local
   notification, UI navigation) are returned as values and executed by the
   caller. Time is never read inside `reduce`; it arrives in the event.
2. **Ordering.** Envelopes are ordered by `(wallClock, device, seq)`. Each
   device applies incoming envelopes by rebuilding state from the merged, sorted
   log (logs are small: tens to low hundreds of events per workout).
3. **Convergence.** Event semantics are chosen so that any two devices with the
   same set of envelopes compute the same state:
   - `setLogged` / `setUnlogged`: latest by ordering wins per set.
   - `setTargetChanged`: last-writer-wins per field per set.
   - `setAdded`: idempotent by `SetID` (generated by the originating device; UUID).
   - `restStarted`: stores an absolute `endsAt`, so both devices show the same
     countdown regardless of when they receive it. `restExtended` adds to
     `endsAt`. `restSkipped` clears it.
   - `finished` / `discarded` are terminal; later events are ignored.
4. **Transport-agnostic.** `LedgerSync` exchanges envelopes (HealthKit workout
   mirroring data channel primarily; WatchConnectivity fallback) and, on
   reconnect, sends "everything from your device with seq > N" so gaps heal.
5. **Persistence.** Envelopes are written to the local event table as they are
   produced or received. On `finished`, `LedgerPersistence` materialises the
   final `WorkoutState` into normalized `workouts` / `logged_sets` rows used by
   history queries. The event log is kept for the workout's lifetime, then
   compacted after successful materialisation.
6. **Recovery.** If either app is killed mid-workout, it replays its local log
   on launch and resumes.

## Alternatives considered

- **State snapshots with last-writer-wins on the whole workout.** Simple but
  loses concurrent edits (watch logs set 3 while phone bumps set 4's weight → one
  is lost). Rejected.
- **Single owner (watch is source of truth, phone read-only during workout).**
  Contradicts the design (phone edits sets, swaps exercises, extends rest).
  Rejected.
- **CRDT library.** Overkill; the event set is small and domain-specific,
  and the rules above give convergence without generic CRDT machinery.

## Consequences

- The engine is trivially unit-testable and property-testable
  (commutativity: shuffle envelope order → same state; idempotence: apply twice
  → same state). This is where most domain test effort goes.
- Slightly more upfront modelling than a mutable `Workout` class, but the
  watch feature, the phone feature, sync, and recovery all fall out of one
  type.
- Timers are wall-clock based (`endsAt`), which also makes Live Activities and
  watch Smart Stack rendering trivial (they take a `Date` and count down).

## Amendment (2026-09-29): hybrid logical clock stamping

Rule 2 orders envelopes by `wallClock`. With raw device clocks, a device whose clock runs behind its
peer's, or steps back after an NTP correction, can stamp an action earlier than the envelope it reacted
to. Replay then applies the two in the wrong order, and a logged set or an un-log is lost on every
device alike (F04 test findings, finding 6).

So the host (F10/F17) stamps every envelope it creates with a hybrid logical clock:

    wallClock = max(now, newest wallClock seen or sent + 1 ms)

An envelope then sorts after every envelope its device had sent or received. That keeps each device's
`seq` order and the causal order (seen before created ⇒ sorts before), while `wallClock` stays close to
real time, which rule 9's rest arithmetic needs. The reducer does not stamp; it takes the stamp as a
precondition (`EventEnvelope.wallClock`). Raw stamps would still converge, but on stamp order.

**The clock rule (F04 fix round 2).** Two clocks travel in an envelope, and they mean different things:

- A **payload time** (`setLogged.doneAt`, `restExtended.tappedAt`, `restStarted.endsAt`,
  `finished`/`discarded` `endedAt`) is the originating device's clock at the action.
- **`wallClock`** is the HLC ordering stamp only. The reducer never reads it as the time of an action
  and never compares a payload time with it to decide behaviour. Its one other use is the sanity bound
  below.

So an event that needs a judgement about time carries the judgement, made on the device where the
screen is known: "+30s" is `restExtended(amount:extendsShownRest:tappedAt:)`. It extends the rest the
lifter saw running, or starts a fresh rest at the tap when the screen showed none (decision #7), whatever
the stamps say. Under skew the HLC can stamp a tap after the end of a rest the lifter still saw running
(F04 test findings, finding 14).

**Malformed envelopes.** An envelope is malformed when its `wallClock` is not finite, a payload date lies
more than 24 h from its `wallClock` (`EventEnvelope.payloadTimeWindow`; a non-finite date never lies within
it), a rest length is outside `0 ... WorkoutEngine.longestRest`, or a `started` snapshot's rest could not
be held by the engine. `reduce` and `replay` ignore it: no state change and no effects. It stays stored,
because the store judges keys, not contents. The 24 h window is generous: it only has to catch absurd
and non-finite times, which would otherwise trap `Duration` arithmetic or break `==` (finding 9).

**Recovery on launch.** The HLC's `newest` must survive a relaunch (rule 6). Before the host stamps any
envelope after a launch, it sets `newest` to the largest stored `wallClock` across the store's uncompacted
logs (`WorkoutEventStore.uncompactedWorkoutIDs`). It skips a stored stamp that its drift bound would reject
on receipt, so a corrupt stamp cannot drag its clock. Without this, a device whose clock stepped back
across a relaunch stamps its next action before its last one, and replay undoes it on every device
(finding 12).

**The host loop.** `reduce` keeps no log, so it must never see an envelope twice. The host appends every
envelope it receives to its store first, then takes what `append` newly stored:

- if all of it sorts after the newest envelope already applied, it reduces it in sort order;
- otherwise it rebuilds once with `replay` of the stored log, which already holds the whole batch.

Effects (finding 13; orchestrator, 2026-09-29):

- envelopes it created: `reduce`'s effects, `.persist` before `.transmit`;
- envelopes it received and reduced in order: `reduce`'s effects without `.persist` and `.transmit`, so a
  set logged on the other device still plays its haptic here (F17 criterion 9);
- a rebuild: only `WorkoutEngine.effects(from:to:)` of the state before and after (materialise, drop the
  log, schedule or cancel the rest notification, update the Live Activity), never a haptic, so a
  reconnect that applies many envelopes at once does not buzz for each.
